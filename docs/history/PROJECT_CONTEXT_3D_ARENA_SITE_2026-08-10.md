# 3D АРЕНА — контекст проекта сайта

Актуализировано: 10 августа 2026 года  
Назначение: единый вводный документ для продолжения работ без повторного разбора переписки.

## 1. Цель проекта

Создать сайт компьютерного клуба 3D АРЕНА, который:

- точно показывает реальный клуб, залы, оборудование, цены и условия;
- помогает гостю быстро выбрать формат и перейти к бронированию;
- сохраняет рекламную атрибуцию до LANGAME;
- корректно индексируется в production;
- развивается безопасно: сначала preview, затем отдельное подтверждение production.

Визуальное направление: **Neo-Russian Arena** — тёмная технологичная среда, крупная типографика, реальные фотографии клуба, синий акцент, сочетание современной киберспортивной эстетики с фирменным русским орнаментом.

## 2. Главные рабочие правила

1. Все изменения сначала проверять на preview.
2. Production публиковать только после отдельного явного подтверждения владельца.
3. Перед каждым релизом проверять фактическую ветку, HEAD, diff и состояние удалённого `main`.
4. Не переносить preview-файлы в production вслепую:
   - preview должен сохранять `noindex,nofollow,noarchive`;
   - production должен сохранять canonical, индексирование, аналитику и служебные файлы.
5. Цены, акции, оборудование, телефоны и расписание менять только по подтверждённому источнику.
6. Статический HTML — источник публичной правды. Не создавать вторую версию цен, CTA или текстов через JS-подмену.
7. Характеристики оборудования — гарантированные факты клуба. Подпись конкретной фотографии описывает только видимое содержимое кадра.
8. В рекламных кабинетах по умолчанию работать только в режиме чтения. Бюджеты, ставки и кампании менять после отдельного разрешения.
9. Не запрашивать и не сохранять в переписке токены, пароли, сертификаты и приватные ключи.

## 11. Технические риски и найденные ошибки

1. Runtime-подмена контента через `release-06.js` создавала вторую версию правды для цен, CTA, метаданных и акций.
2. В `release-06.js` был дублирован `const depth`, что могло ломать выполнение JavaScript.
3. Контент, доступный только после выполнения JS, ухудшает надёжность, SEO и доступность.
4. HTTP 200 подтверждает только доставку, но не корректный рендеринг. Нужно проверять CSS, изображения, `naturalWidth`, консоль и реальный браузер.
5. GitHub Pages после merge может временно отдавать старую HTML-версию. Нужны ожидание и повторная проверка.
6. Draft PR нельзя объединять напрямую: сначала перевести его в ready.
7. В старой локальной версии Git отсутствует `git switch`; использовать `git checkout -b`.
8. При конфликте preview/production сохранять production-метаданные и переносить только согласованный контент.

## 13. Доступы и безопасность

- GitHub CLI был повторно авторизован под аккаунтом `DubasV`.
- В ограниченной среде проверка `gh auth status` может ошибочно показывать проблему из-за недоступности macOS Keychain; в разрешённом окружении авторизация работала.
- GitHub-операции проводить через отдельную ветку и PR.
- VK-токен однажды попал на скриншот. Его содержимое нигде не сохранять и не повторять. Такой токен нужно отозвать или заменить.
- Ошибка LANGAME `ERR_SSL_CLIENT_AUTH_SIGNATURE_FAILED` была связана с отсутствием пригодной TLS-идентичности с приватным ключом. Для исправления нужен корректный `.p12`/`.pfx`, а не публичный сертификат.

## 17. Критерий качества

Сайт считается готовым к следующему релизу, когда:

- факты совпадают с реальным клубом;
- два зала визуально различимы;
- основное действие понятно без объяснений;
- контент доступен без обязательной JS-подмены;
- мобильная версия не теряет смысл и CTA;
- атрибуция доходит до бронирования;
- preview закрыт от индексации;
- production индексируется и сохраняет аналитику;
- публикация прошла отдельное подтверждение и live-проверку.
